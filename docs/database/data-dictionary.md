# Mosaic data dictionary

The SQL snapshot is in `schema.sql`. All IDs are opaque UUID-style strings generated by the application. Timestamps use ISO-8601 UTC strings. JSON columns are validated at the API boundary and with SQLite `json_valid()`.

| Entity | Purpose | Key invariants |
|---|---|---|
| `workspaces` | One user's private library and settings boundary | MVP is single-user/local; workspaces still provide logical isolation |
| `provider_policies` | Versioned permission decision for a provider/product | `unreviewed` defaults to no indexing, derivation, strategy analysis, or cross-provider transfer |
| `source_artifacts` | Original imported archive or pasted source | Hash, source type, parser version, policy status, and retention state retained |
| `conversations` | Provider-neutral conversation record | Linked to source artifact where available; provider ID may be unknown |
| `messages` | Ordered message and optional branch structure | Role and sequence validated; original text kept separate from derived summary |
| `episodes` | Coherent sub-problem inside a conversation | Links to one conversation and a range of sequence numbers |
| `episode_messages` | Explicit episode membership | Allows non-contiguous or branch-aware membership |
| `knowledge_items` | Typed semantic records | Candidate by default; personal/general scope; interpretation class explicit |
| `knowledge_evidence` | Provenance and supporting/challenging material | Claims and findings must have evidence or remain hypotheses |
| `knowledge_relations` | Typed relationships between knowledge items | Suggested relations remain candidate until reviewed |
| `procedures` | Versioned reusable methods | Status separate from associated knowledge item's status |
| `procedure_steps` | Ordered procedure instructions | Steps are immutable within a procedure version |
| `objectives` | Long-running task/project intent | Version changes when constraints/goal materially change |
| `coordination_sessions` | One provider contribution in a multi-model objective | Provider/model attribution can be unknown; no credentials stored |
| `context_packets` | Exact content prepared for handoff | Versioned, hashed, user-previewable, and destination-labelled |
| `model_responses` | User-returned provider response | Provider is derived from the context packet attached to the session; attribution is user-attested, not cryptographically verified; stored as untrusted input |
| `feedback_events` | Explicit user or verified task feedback | Silence is not feedback; event identifies target and source |
| `benchmark_suites` | Versioned collection of evaluation cases | Test split policy is documented and immutable per suite version |
| `benchmark_cases` | One evaluation case with expected result | Holdout cases cannot be used for candidate tuning |
| `experiments` | Pre-registered comparison of baseline and candidate | Includes hypothesis, protocols, evaluator version and promotion state |
| `experiment_runs` | Result for one test case/procedure | Links back to test case and procedure version |
| `model_observations` | Conditional model/strategy performance evidence | Includes task category, model/version, evaluation method and outcome |
| `processing_jobs` | Durable import/analysis task state | Retries must be idempotent; errors must not expose secrets |
| `audit_events` | Minimal operation history | Never place full transcript, full packet, or secret values in audit details |

## Status semantics

### Knowledge item

- `candidate`: generated but not reviewed.
- `user_confirmed`: user confirmed the interpretation; this does not necessarily prove a factual claim.
- `source_supported`: the source supports what the item says; source accuracy may still be unverified.
- `experiment_supported`: an explicit experiment supports the defined claim in its stated scope.
- `active`: approved for retrieval/use in the operational knowledge base.
- `disputed`: material conflicting evidence exists.
- `rejected`: user/evaluator rejected the item.
- `deprecated`: superseded or stale, retained for history.
- `withdrawn`: source or permission withdrawal invalidated the item.

### Procedure

- `candidate`: extracted or proposed procedure.
- `experimental`: currently being evaluated.
- `validated`: passed a defined evaluation in a bounded scope.
- `active`: approved for ordinary use within stated conditions.
- `rejected`: failed its evaluation or was rejected.
- `superseded`: replaced by a later version.
- `withdrawn`: no longer permitted or supported.

## Notes on evidence

`source_supported` means “accurately represented by the cited source,” not “universally true.” A provider-generated answer is evidence that the provider made a statement; it is not independent verification that the statement is correct. Model agreement is not independent evidence unless the underlying sources and methods are independent.

## Deletion notes

Deletion must consider source files, message rows, FTS indexes, extracted knowledge, relationships, episodes, context packets, backups, and exports. The audit log may retain a minimal deletion tombstone, but not deleted content. Backups are separate copies and require an explicit retention/expiry policy.


## `analysis_handoffs`

Server-issued, expiring, single-use records binding a semantic-analysis packet to one workspace, source conversation/provider, and destination provider. The stored `content_hash` fingerprints the outbound packet for audit; it does not authenticate a response from the destination AI service. Manual-destination ingestion requires an explicit user-authorship attestation; external-destination ingestion requires local-storage consent. `destination_provider` is applied to extracted candidates from the server-side handoff record, never accepted as a client-supplied field. The value represents the user's attested destination, not an authenticated statement from the provider. A handoff is consumed in the same SQLite transaction that persists its candidate knowledge.
